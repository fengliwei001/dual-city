## 4. 信息架构原则

1. **3 次点击原则**：任何动作 3 步内可达（浏览 → 报名/发需求 → 进群/被撮合）；
2. **标签为王**：标签贯穿「资料卡 → 筛选 → 匹配」全链路，是唯一结构化信息纽带；
3. **社区优先于撮合**：默认路径引导先认识人（进群），撮合是辅助；
4. **文案集中**：品牌名、玩法术语、城市名做成配置，便于改名；
5. **双入口不冲突**：「先认识」「先匹配」最终都汇入同一群/同一批人。

## 5. 数据模型（V1 轻量版）

### 5.1 实体关系

```
User (用户/访客)
  ├── Signup (报名记录) 1..1
  ├── Profile (资料卡) 0..1
  │     └── Tags (标签关联, M:N)
  ├── Demand (需求单) 0..N
  └── MatchResult (匹配结果) 0..N (查询即得, 可不落库)

City (城市) ← 四城 + 其他
TagDict (标签字典) ← 13 类预设 + 自定义
Route (线路) ← 四城线路内容
Scene (场景页内容) ← A/B/C 配置化
```

### 5.3 匹配计算（V1 规则）

```
score = w1 * city_match(目标城市=常驻城市)
      + w2 * tag_overlap(需求标签 ∩ 资料卡标签)
      + w3 * form_match(线上/线下一致)
      + w4 * reciprocity(我的offer ∩ 对方想学/想要的)
权重默认: w1=0.4, w2=0.3, w3=0.1, w4=0.2 (运营可调)
```

## 7. 二级菜单（关键交互路径）

> 用户重点要求：**一级菜单下点击进去有三个二级菜单 A/B/C，且二级菜单带匹配/报名/私信等产品能力**。

| 二级菜单 | 主要产品动作 | 承载页面 |
| --- | --- | --- |
| A. 深圳人想去云南有人带 | 发旅居需求 / 报名 / 找带玩者（匹配） | /scenes/sz-to-yn → /demands/new → /match |
| B. 云南本地人想学 AI | 发学习需求 / 报名 / 找教学者（匹配） | /scenes/yn-learn-ai → /demands/new → /match |
| C. 双方交朋友、建圈子 | 浏览资料卡 / 进群 / 报名活动(二期) | /scenes/community → /people → /join |

**闭环设计**：
- 场景 A/B 的「发需求」→ 进入匹配（找带玩者/教学者）；
- 场景 C 的「进群」→ 私域社群承接交友；
- 二期补「私信」后在资料卡/匹配结果直接发起会话，闭环更完整。
